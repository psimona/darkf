## Pass 1 (2026-10-22) — spec-review
Auto-fixed 4 issues, all verified directly against the code, not assumed:

1. (HIGH) `NodeStatus` union (`darkf-core/src/types.ts`) was never stated
   to need its 5th variant (`{ phase: "failed"; result: NodeResult }`),
   despite the spec's own code snippet requiring it for `emit()` to
   type-check. Fixed: stated explicitly as a prerequisite in §2.
2. (HIGH) `darkf-cli` surface area understated — 6 call sites verified by
   reading the code (`RegistryStatus`, `TerminalOutcome`+`journalTerminal`,
   `TerminalState`, `foldJournal`'s `hasEnd`/`finalResult` — EXIT-gated,
   would silently leave a failed run's `hasEnd` false — `foldReport`'s
   fold, which silently drops a `failed`-phase dispatch with no catch-all,
   and the status→exit-code switch). Fixed: added §2a naming all 6 and
   the two silent-failure risks explicitly.
3. (HIGH) Open Questions' own suggestion of exit code 3 for `failed`
   collides with `"running"`'s existing exit code 3 in the exact switch
   function that would need the new case — verified against
   `darkf-cli/src/index.ts`. Fixed: corrected in Open Questions, with the
   collision stated and 4 suggested instead (pending a consistency check
   against `monitorCmd`'s separate exit-code space).
4. (MEDIUM) Mermaid rendering of `[-]` was framed as a cosmetic "needs a
   display name" open question. Verified `darkf-core/src/mermaid.ts:15`:
   `[*]` is `stateDiagram-v2`'s one hardcoded pseudostate token, not a
   convention — unhandled, `FAILED` renders as a literal broken node, not
   an unlabeled terminal. Fixed: moved to Design §2b as a required change.

Also added a `## Downstream` section (LOW, discoverability) naming the two
specs now blocked on this one (`workflow-validation`, and
`completion-phase-port` in the consumer repo), mirroring the `## Dependency`
sections those two specs already carry pointing back here.

One self-correction during drafting: an early edit of §2b incorrectly
attributed a "FAILED is never valid as initial" rule to this spec itself.
That rule doesn't exist here — it's `workflow-validation`'s future job
(already captured by its own `## Dependency` note), not something this
spec needs to state or enforce. Removed before finalizing.

No open issues after pass 1. Spec was ready for `/council`.

## Pass 2 (2026-10-22) — /council review
Convened: Devil's Advocate, Optimist, Realist, Runtime/Engine Internals,
Build/Tooling Engineer. Record: docs/council/2026-10-22-0755-failed-terminal.md

Verdict: adopt, but 4 blocking items found — not yet fixed in the spec:

1. (Convergent: Devil's Advocate + Realist) EXIT alias lifetime has no
   decided window or enforcement mechanism (lint/CI check) — risks
   becoming permanent.
2. (Convergent: Devil's Advocate + Realist) Exit-code choice left as an
   open question into implementation — risks mid-PR scope creep.
3. (Runtime/Engine Internals, single-lens, code-verified, highest
   priority) FAILED-check placement in run.ts must come BEFORE the
   registry.has(nextTarget) unresolved-target guard (line 308), same as
   EXIT does today (line 301). Spec's "beside the EXIT branch" phrasing
   is ambiguous; placed after, every FAILED route silently crashes as
   unresolved-target instead of grading failed — defeats the spec.
4. (Build/Tooling Engineer, single-lens, code-verified, highest
   priority) `commit_failed -> retry -> run_failure` is not
   implementable as stated: def.retries doesn't bound an ordinary
   on-edge self-loop (only the internal crash/timeout retry loop, which
   resets on re-entry). Needs an explicit maxCycles mandate on the 6
   commit-node composites, or drop "retry" and route straight to
   run_failure like the other ~14 edges.

Non-blocking, tracked: no durable guardrail for future give-up edges
(enumerated, not principled); run_failure's dirty-artifact commit with no
repair path; failed-scope retry with no run-level cap; external
raw-marker consumers can't distinguish DONE/FAILED (darkf-cli's typed fix
doesn't reach them) — all Devil's-Advocate-only, unconfirmed by other
lenses, noted as risks to watch.

Items 1-3 applied directly to the spec, grounded against live code:

1. EXIT alias lifetime decided concretely: grepped every non-test EXIT
   usage (5 workflow-authoring call sites, all internal to darkf — zero
   in the consumer repo). Darkf's 5 renamed to DONE in this spec's own PR; alias
   kept solely for the consumer repo's pending Slice 2 migration, deleted in the
   same PR that lands Slice 2. Enforcement is the TypeScript compiler
   (deleting the export), not a new lint/CI rule.
2. Exit codes decided: status→4 (first free slot in statusExit),
   monitor→3 (its one free slot — independent switches, matching the
   existing status/monitor numbering mismatch already present for
   "running" vs "still running"). Found 2 additional call sites while
   verifying (monitorCmd's "terminal" case, monitorRun's poll loop) that
   silently relabel failed as crashed today — added to §2a.
3. FAILED-check ordering made an explicit constraint in §2 (must precede
   the registry.has(nextTarget) guard, mirroring EXIT), with a required
   engine test named directly.

Item 4 (commit_failed/retry/maxCycles) deliberately NOT applied here, on
user instruction: it's a the consumer repo workflow-authoring decision (which
composites, what bound, or simplify the edge), not a darkf-engine change.
Moved to a new "Deliberately deferred" section in the spec, scoped to
Slice 2, rather than left as an unexamined open question — satisfies the
council's "don't carry blocking items as deferred open questions" by being
an explicit, reasoned deferral with an owner (the consumer repo Slice 2), not a
silent gap.

Status: clean — engine-scope items (1-3) closed. Item 4 explicitly
deferred to the consumer repo's Slice 2, out of scope for this spec/repo.
